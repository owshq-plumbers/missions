# 000 — Modelo de referência

> **Isto não é uma Mission real.** É o formato que toda Mission segue. Use como gabarito ao escrever a Mission 001.
>
> Os textos entre `⟨ ⟩` são os que mudam a cada Mission.

---

## O caso

⟨ Duas ou três frases descrevendo uma situação real, do jeito que ela chegaria numa empresa. Sem enunciar a solução. Sem listar as tecnologias. ⟩

**Exemplo do tom pretendido:** *"Uma operação de e-commerce descobriu que o relatório de receita diária diverge do extrato do gateway de pagamento em alguns dias do mês. Ninguém sabe desde quando. O time de dados foi chamado para explicar a diferença antes do fechamento contábil."*

Repare no que o exemplo **não** faz: não diz para usar dbt, não diz que é problema de fuso horário, não diz qual o resultado esperado. Uma Mission que já contém a resposta na pergunta não avalia nada.

## O que você recebe

⟨ Insumos em `dados/`: amostras, esquemas, um dump, um endpoint de teste, logs. O que existiria de verdade. ⟩

## O que se espera de você

⟨ O entregável, em termos de resultado — não de tecnologia.

Exemplo: *"Uma explicação da divergência que sustente uma conversa com o financeiro, e um mecanismo que detecte o problema antes do fechamento do próximo mês."*

Se a Mission exigir uma tecnologia específica, diga aqui **e diga por quê**. Restrição sem motivo vira pegadinha. ⟩

## Restrições

⟨ O que não vale. Exemplos: "não use serviço pago", "precisa rodar na máquina de quem revisa com um comando", "não altere os dados de origem". ⟩

## Tempo estimado

⟨ Uma faixa honesta. Se você não sabe, não invente — diga que é a primeira turma e que o tempo será calibrado. ⟩
